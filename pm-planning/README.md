# PM / 기획 — GitHub Copilot CLI 실무 시나리오

> **GitHub 이슈/PR 진행 상황 리포팅, 회의록 → 액션 아이템 추출, 릴리스 노트 초안** 등 프로젝트 매니저·기획자가 반복 수행하는 업무를 CLI 로 처리하는 3가지 시나리오.

이 폴더는 [메인 가이드](../README.md) 의 PM / 기획 편입니다. **설치·인증·안전 수칙은 [메인 문서](../README.md)를 먼저 읽어주세요** (특히 [8번 안전 수칙](../README.md#8-반드시-알아야-할-안전-수칙)).

PM/기획 직군은 **GitHub 저장소·이슈·PR 을 자연어로 다루는** 기능을 가장 많이 활용합니다. Copilot CLI 는 GitHub API 를 내장하고 있어 별도 설정 없이 저장소를 조회·조작할 수 있습니다.

---

## 각 시나리오 읽는 법

- **상황** — 어떤 문제인가
- **프롬프트** — 그대로 복사해서 붙여넣을 수 있는 한국어 명령
- **결과** — 무엇을 받게 되는가
- **팁** — 반복 사용 / 안전 팁

**전제**: 아래 예시들은 모두 대화형 모드(`copilot`) 안에서 입력합니다. GitHub 저장소를 다루는 시나리오는 해당 저장소에 대한 **read 권한이 있는 계정으로 로그인** 되어 있어야 합니다.

## 시나리오 A. GitHub 이슈 목록을 진행 상황 리포트로 변환

**상황**: 팀이 쓰는 GitHub 저장소의 열린 이슈들을 주간 리포트로 정리해야 함.

**프롬프트**:
```
octo-org/octo-repo 저장소의 지난 7일간 open/closed 된 이슈들을 정리해서
weekly_status.md 를 만들어줘.

포함할 내용:
- 이번 주 종료된 이슈 (제목/담당자/PR 링크)
- 이번 주 새로 열린 이슈 (우선순위 순)
- 오래 열려있는 이슈 (30일 이상)
- 주요 이정표별 진척률 (label = milestone:* 기준)
- 다음 주 예상 완료 후보 (in-progress 이면서 오래된 것)

Executive summary 는 3줄로 최상단에.
```

**결과**: 주간 회의 자료로 바로 붙여넣을 수 있는 `weekly_status.md`.

**팁**: Copilot CLI 는 GitHub API 를 내장하고 있어 이슈/PR 을 자연어로 다룰 수 있습니다. 저장소명(`octo-org/octo-repo`) 만 실제 것으로 바꾸고, 필요하면 특정 label / assignee / milestone 조건을 추가하세요.

## 시나리오 B. 회의록 요약 → 액션 아이템 추출

**상황**: 지난주 회의록 5개(각 3~5페이지 마크다운) 에서 액션 아이템만 뽑아 담당자별로 정리.

**프롬프트**:
```
./meetings/2026-W30/ 폴더의 모든 회의록(.md)을 읽어서
아래 액션 아이템 표를 만들어줘 (actions_W30.md):

- 담당자
- 액션 아이템 (원문에서 그대로 인용)
- 마감일 (원문에 명시된 경우만, 없으면 "미지정")
- 관련 회의 (파일명과 회의 날짜)
- 우선순위 (원문에서 유추, high/medium/low)

담당자별로 그룹핑해서 마크다운 표 여러 개로 정리.
마지막에 "마감일이 미지정된 액션 목록" 을 별도 섹션으로.
```

**팁**: 매주 같은 프롬프트로 재사용 가능. 폴더 경로 (`2026-W30`) 만 그 주에 맞게 바꾸면 됩니다. 담당자별 그룹핑 결과를 Slack/Teams 에 그대로 붙여넣어 팔로업.

## 시나리오 C. 릴리스 노트 자동 초안

**상황**: 이번 스프린트에서 머지된 PR 12건으로 릴리스 노트 초안 작성.

**프롬프트**:
```
octo-org/octo-repo 에서 지난 2주간 main 브랜치에 머지된 PR 을 모두 뽑아서
release_notes_v2.14.md 초안을 만들어줘.

포맷:
## New Features
- (PR 제목, #번호, 담당자)

## Improvements
- ...

## Bug Fixes
- ...

## Breaking Changes (있으면)
- ...

각 PR 의 body 를 참고해서 사용자 관점의 한 줄 설명으로 재작성.
내부 리팩토링 PR (label:internal) 은 제외.
```

**팁**: 초안이 나오면 검토·수정 후 그대로 릴리스에 사용. 매 스프린트 같은 프롬프트 재사용. PR 제목/설명 작성 규칙을 팀에서 통일해두면 자동 분류 정확도가 크게 올라갑니다.

## PM / 기획 실무자 추천 프롬프트 패턴

1. **날짜·기간 명시** — "지난 7일간", "2026-W30" 등 구체적으로. "최근" 같은 모호한 표현 피하기
2. **Executive summary 별도 요청** — 임원/리더 대상 3줄 요약을 항상 최상단에
3. **원문 인용 유지** — 회의록 액션 아이템은 요약보다 원문 그대로 인용이 안전 (책임 소재 명확)
4. **label / milestone / assignee 필터** — GitHub API 쿼리는 조건을 구체적으로 주면 정확도가 훨씬 높음
5. **마크다운 표 형식으로 요청** — Notion / Confluence / Slack 어디에나 붙여넣기 가능
6. **`.github/copilot-instructions.md` 파일에 팀 규칙 저장** — 저장소별 라벨링 규칙, PR 컨벤션 등을 미리 두면 모든 팀원의 프롬프트가 일관됨 (`copilot init` 로 초기 생성)
7. **주간/스프린트 리포트는 프롬프트 자체를 자산화** — 팀 위키에 "주간 리포트 프롬프트" 로 저장, 매주 그대로 재사용
